# ADR-0002: 計測データの記録方式 — 手動記録を行わない

| 項目 | 内容 |
|---|---|
| ステータス | **承認** |
| 決定日 | 2026-07-20 |
| 決定者 | Kazuyuki Kuribayashi |
| 影響範囲 | `dogfooding-roadmap.md` 第4章、`docs/psp-data/` の運用 |
| 関連 | [ADR-0001](adr-0001-data-collection-first.md)（実装順序をデータ収集先行に変更） |

---

## 1. 背景

### 前提となる決定

[ADR-0001](adr-0001-data-collection-first.md) により、実装順序をデータ収集先行に変更した。
この移植プロジェクト自体を PSP で計測し、そのデータを Processloop に投入する方針である。

その際、M1（記録できるツールの完成）までの期間は **CSV による手動記録**で
データを蓄積する案を併記していた。本 ADR はその手動記録について再検討した結果である。

### 検討のきっかけ

M1 着手にあたり、直近の作業として3案を比較した。

| 案 | 内容 | 所要 |
|---|---|---|
| 案1 | `docs/psp-data/` に CSV を置き、A-1 を遡及登録 | 30分〜1時間 |
| 案2 | `frontend` の初期化 | 1〜2時間 |
| 案3 | Prisma スキーマから M1 の実装 | 数日 |

比較の過程で、次の2点が明確になった。

**1. M1 の66%は frontend なしで着手できる**

依存関係を調べた結果、Prisma・hier・フェーズ一覧読み込み・時間ログ（計1,750行）は
UI に依存しないドメインロジックだった。案2を先に行う必然性は薄い。

**2. 案2では記録できるようにならない**

`create-next-app` が生成するのは空の枠であり、記録に必要な
Prisma スキーマ・計測ロジック・画面はいずれも含まれない。
**記録が可能になるのは、どの順序で進めても M1 完成時**である。

### 手動記録の負担

M1 完成までの期間、CSV へ手作業で記録するには次が必要になる。

- 作業のたびに開始・終了・中断時刻を控える
- 中断を除いた正味時間を計算して1行追加する
- 欠陥が出るたびに混入フェーズ・発見フェーズ・分類を記録する

**分単位の記録を毎日続けることは、現実的に困難である。**
記録が途切れれば、データの一貫性も失われる。

### 見落としていた事実

再調査により、**devlog が既に PSP データの原型を含んでいる**ことが判明した。

| devlog の章 | 対応する PSP データ | 4ファイルでの分量 |
|---|---|---|
| つまずき→解決の記録 | 欠陥ログ（混入・発見・内容） | 309行の表 |
| 調査・実測の記録 | 規模データ（見積り・実績） | 同上に含まれる |
| 決定ログ | — （PSP データではないが設計判断の記録） | 同上に含まれる |

実際、A-1 の欠陥4件と規模1件は devlog から抽出できた。

⚠️ ただし**作業時間だけは devlog に記録されていない**ことも確認した。

---

## 2. 決定

**M1 完成までの期間、CSV への手動記録は行わない。**

具体的には次のとおりとする。

| # | 内容 |
|---|---|
| 1 | **A-1 の実績は devlog から遡及抽出し、`docs/psp-data/` に登録する**（一度きりの作業） |
| 2 | M1 完成までの期間、逐次の手動記録は**行わない** |
| 3 | 代わりに **devlog の作成を継続**し、M1 完成後に遡及抽出して一括投入する |
| 4 | M1 完成以降は、**Processloop 自身の UI で記録する** |

---

## 3. 理由

### 既に続いている記録を活用する

devlog は 2026-07-18 から毎日作成しており、**運用が定着している**。
新たに手動記録を始めるより、既存の記録から抽出する方が確実である。

「続かない記録を新設する」より「続いている記録を活かす」方が、
データが失われるリスクが低い。

### 二重管理を避ける

devlog と CSV の両方に同じ欠陥を書くと、内容がずれたときにどちらが正か分からなくなる。
記録の入口を一本化する。

### 遡及抽出が実際に機能することを確認済み

A-1 について、devlog から欠陥4件と規模1件を抽出できた。
同じ手順が A-2 以降にも適用できる。

### ツールの完成を早めることが最大の対策になる

手動記録の期間が短いほど、失われるデータは少ない。
記録の仕組みを整えるより、**M1 を早く完成させる**方に労力を向ける。

---

## 4. 検討した代替案

### 代替案1：CSV への手動記録を続ける

**内容**：ADR-0001 に併記していた案。作業のたび CSV に1行追加する。

**利点**：時間データを含む完全な記録が得られる。

**却下理由**：分単位の記録を毎日続けるのは負担が大きく、途切れるリスクが高い。
また devlog との二重管理になる。

### 代替案2：記録を一切行わない

**内容**：M1 完成まで何も記録せず、以降のデータのみを扱う。

**却下理由**：A-1 の材料は devlog に既にあり、抽出コストは30分程度である。
これを捨てるのは合理的でない。また devlog を書き続ける以上、
M1 完成後に遡及抽出できる材料は自然に蓄積される。

### 代替案3：devlog に作業時間の1行を加える

**内容**：devlog の末尾に「本日の作業時間: 約X時間」を1行だけ追加する。

**利点**：ほぼゼロコストで、粗い時間データが残る。
CSV への逐次記録とは負担が桁違いである。

**扱い**：**採否は保留**とする。本 ADR の決定を妨げるものではなく、
必要と判断した時点で devlog スキルに追記すればよい。

## 5. 影響

### 変わるもの

| 対象 | 変更内容 |
|---|---|
| `dogfooding-roadmap.md` 第4章 | 「手動記録フェーズ」→「記録方式」。逐次記録の手順を削除 |
| `dogfooding-roadmap.md` 第10章 | 直近の行動案から「手動記録を開始する」を削除 |
| `docs/psp-data/` の位置づけ | 日々の記録先 → **A-1 の遡及登録と、将来の一括投入先** |

### 変わらないもの

- ADR-0001 の決定（実装順序はデータ収集先行のまま）
- M1〜M6 の構成
- 移植仕様書のセクション5「実績記録」を設ける方針
- CSV の様式（Prisma スキーマに対応させる設計）

### ⚠️ 受け入れる限界

**M1 完成までの期間、作業時間のデータが欠損する。**

devlog は作業時間を記録していないため、遡及抽出では時間を回収できない。
回収できるのは規模と欠陥のみである。

この影響を評価すると次のようになる。

| 用途 | 必要なデータ | 影響 |
|---|---|---|
| **PROBE の回帰** | 見積り規模 vs 実績規模 | **なし**（規模は回収できる） |
| 欠陥分析（混入・除去） | 欠陥の分類と工程 | **なし**（欠陥は回収できる） |
| フェーズ別の時間配分 | 工程ごとの作業時間 | **M1 まで分析不可** |
| EV（計画対実績） | 計画時間と実績時間 | M1 まで分析不可 |

**PROBE の主入力である規模データは失われない**ため、ADR-0001 の目的
（PROBE を自分のデータで検証する）は達成できる。

### 捏造しないこと

遡及登録において、**記録がない項目は空欄とする**。

A-1 の欠陥について、修正に要した時間は devlog に記録がない。
推測値を入れると PSP の分析が歪むため、`fix_min` は空欄とする。
