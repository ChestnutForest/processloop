# ADR-0001: 実装順序をデータ収集先行に変更する

| 項目 | 内容 |
|---|---|
| ステータス | **承認** |
| 決定日 | 2026-07-20 |
| 決定者 | Kazuyuki Kuribayashi |
| 影響範囲 | 第1期の実装順序、`deliverables-proposal.md` 第3章 |

---

## 1. 背景

### プロジェクトの性質

Processloop は Process Dashboard（GPLv3）を Next.js へ移植するプロジェクトである。
移植元は PSP（Personal Software Process、個人ソフトウェアプロセス）を支援するツールであり、
開発者が自分の作業時間・欠陥・成果物規模を記録し、そのデータから見積りと品質を改善する手法を扱う。

### 当初の実装順序

移植着手前の調査（2026-07-18〜19）により、計算式エンジンが5層構造であることが判明した。

```
dataFile.txt → プリプロセッサ → 動的マクロ生成 → パーサ → 評価器 → DataRepository
```

この構造を踏まえ、**計算エンジン（A群7ユニット）から着手する**順序を採用した。
2026-07-20 に A-1（プリプロセッサ）の実装が完了している。

### 変更のきっかけ

成果物の定義を議論する中で、移植仕様書に「実績記録」セクションを設ける案が出た。
各ユニットで見積り行数・実績行数・所要時間・発生した欠陥を記録すれば、
**この移植プロジェクト自体を PSP で計測できる**という発想である。

完成後に自分自身の実データを Processloop へ投入すれば、ドッグフーディングの素材になる。
この案が承認されたことで、「ではドッグフーディングをいつ始められるか」という問いが生じた。

---

## 2. 決定

**第1期の実装順序を、計算エンジン先行からデータ収集先行に変更する。**

具体的には、次の6マイルストーンで進める。

| M | 内容 | 到達点 |
|---|---|---|
| **M1** | 永続化・階層・時間ログ・最小UI | **時間を記録できる（ドッグフーディング開始）** |
| M2 | 欠陥ログ | PSP の3大生データが揃う |
| M3 | 計算エンジン（A群 ＋ util ＋ Templates変換） | 派生指標が自動計算される |
| M4 | PROBE | 蓄積データで見積もれる |
| M5 | EV | 計画対実績・完了予測 |
| M6 | 仕上げ（サマリ画面・E2E・マニュアル・デプロイ） | 第1期完了 |

---

## 3. 理由

### 決定的な理由：PROBE は履歴データがないと検証できない

PROBE（PROxy Based Estimating）は、過去の「見積り規模 vs 実績規模」の組に
線形回帰をかけて次の見積りを導く手法である。t分布を用いて予測区間も算出する。

つまり **PROBE を実装しても、履歴データがなければ何も出力できない**。

当初の順序では、PROBE（B-6）に着手する頃には第1期の大半が終わっている。
そこから記録を始めても、自分のプロジェクトで PROBE を検証する機会が残らない。

データ収集を先行させれば、B-6 到達時点で**十数ユニット分の実データ**が蓄積される。
回帰分析が実際に意味を持ち、実装の正しさを自分のデータで確認できる。

同じことが EV（B-7 / B-8）にも当てはまる。計画対実績の比較は、
計画と実績の両方が記録されていて初めて成立する。

### 順序変更を可能にする構造的事実

調査により、**生データの記録は計算エンジンから独立している**ことが確認できた。

| 種別 | 内容 | エンジン依存 |
|---|---|---|
| 生データ | 作業時間、欠陥、成果物規模 | **なし** |
| 派生指標 | 歩留まり、欠陥密度、CPI/SPI、PROBE の回帰 | あり |

`timelog.xml` や欠陥ログは、それ自体が完結した記録である。
エンジンはこれらを入力として派生指標を計算する層であり、記録そのものには関与しない。

したがって、記録機能を先に作っても**エンジンの設計に影響しない**。

### 副次的な理由

**データモデルの早期検証** — `HierarchyNode` / `TimeLogEntry` / `Defect` の設計が
実用に耐えるかは、使ってみないと分からない。終盤で判明すると手戻りが大きい。

**動機の持続** — 第1期は19,000行を超える長い道のりである。
途中で自分のデータが見えるものがあると続けやすい。

**ツール自体の説得力** — 「PSP のツールを作ったが、開発中は PSP を使っていない」
という状態は避けたい。

## 4. 検討した代替案

### 代替案1：現行維持（計算エンジン先行）

**内容**：A-1 から A-7 まで順に進め、その後 B群・C群へ。

**利点**：A-1 完了直後で文脈が続いている。調査（`grammar.txt` 28規則、
Signals の採用判断、Peggy の選定）の勢いを断たない。

**却下理由**：PROBE と EV を自分のデータで検証できない。
ドッグフーディングが第1期の終盤になり、蓄積データがほぼゼロになる。

### 代替案2：折衷（A-3 まで進めてから M1 へ）

**内容**：値の型システム（約600行）を終えてから、データ収集へ移る。

**利点**：型定義はエンジン全体の土台であり、区切りが良い。

**却下理由**：600行分ドッグフーディングが遅れる割に、得るものが
「区切りの良さ」にとどまる。型システムは M3 で着手しても支障がない。

### 代替案3：手動記録のみで済ませる

**内容**：CSV での手動記録を第1期の全期間続け、完成後に一括投入する。

**利点**：実装順序を変えなくてよい。

**却下理由**：記録が続かないリスクが高い。またデータモデルの検証機会が
得られず、投入時に形式が合わない可能性がある。

## 5. 影響

### 変わるもの

| 対象 | 変更内容 |
|---|---|
| `deliverables-proposal.md` 第3章 | 第1期a/第1期b の分割を、M1〜M6 に置き換え |
| frontend の初期化時期 | 第1期終盤 → **M1 に含める（直近の作業）** |
| 手動記録の期間 | 第1期の全期間 → M1 完成まで |

### 変わらないもの

- **18ユニットの定義**（A群7・B群10・C群1）
- **総実装量**（順序の変更のみ。捨てる作業は1行もない）
- 移植方針（案A：計算式エンジンごと移植）
- 技術選定（Peggy、`@preact/signals-core`、Prisma）
- 成果物の種類とトレーサビリティの構造

### 副次的に判明した事項

本決定の検討過程で、**第1期の実装規模の記載に誤りがあること**が判明した。

| | 誤（従来の記載） | 正（18ユニットの積み上げ） |
|---|---|---|
| 第1期の実装規模 | 7,200〜9,800行 | **19,000〜21,000行** |

個別ユニットの見積りは移植元の実行数から算出した根拠あるものであり、
合計値の記載が誤っていた。関連文書を併せて訂正する。

この訂正は本決定の理由を強めこそすれ、弱めない。
規模が倍以上であるなら、**途中で成果が見える構成の価値はさらに高くなる**。

## 6. リスクと対処

### リスク1：UI が計算エンジン導入時に手戻りする

M1 で作る画面の表示内容が、M3 のエンジン導入後に変わる可能性がある。

**対処**：集計処理をエンジンで置き換えやすい形に隔離する。

```typescript
// M1: 直接計算
export function totalTime(entries: TimeLogEntry[]): number { … }

// M3 以降: エンジン経由に差し替え
export function totalTime(path: string): number {
  return repository.getValue(`${path}/Time`);
}
```

呼び出し側のインタフェースを変えなければ、差し替えは局所的に済む。

### リスク2：文脈の切り替えコスト

エンジンの調査・実装から UI 側へ移ると、頭を切り替える必要がある。

**対処**：調査済みの資産は失われない。`grammar.txt` の分析も Signals の判断も
M3 でそのまま使える。保留になるだけで無駄にはならない。

### リスク3：記録の手間が続かない

手動記録は面倒である。

**対処**：M1 を早く終わらせることが最大の対策になる。
それまでは粒度を粗くしてよい（1日1行でも記録がないよりよい）。
