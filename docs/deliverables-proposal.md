## 0. 前提の整理

### 開発フェーズ（確定済み）

| フェーズ | 内容 | 実装規模 |
|---|---|---|
| **第1期** | 個人の PSP 機能 ＋ PROBE ＋ EV | 19,000〜21,000行 |
| 第1.5期 | 実用性の底上げ | 2,000〜3,000行 |
| 第2期 | 汎用チームプロセス機能 | 8,000〜12,000行 |
| 第3期 | 高度なチーム機能 | 5,000行〜 |

### 工程と成果物の対応（ご指定の⑤）

```
要求定義          → 要求仕様書
アーキテクチャ設計 → アーキテクチャ仕様書
プログラム設計    → プログラム仕様書
実装             → Processloop 本体のソースコード
単体テスト        → 単体テスト仕様書 ＋ 単体テストプログラム
結合テスト        → 結合テスト仕様書 ＋ 結合テストプログラム
総合テスト        → 総合テスト仕様書 ＋ E2Eテストプログラム
デプロイ          → Web サービス
```

### 移植プロジェクト固有の事情

新規開発と異なり、**要求の源泉は移植元の挙動**である。したがって全工程の上流に「①移植元の解析」が入る。

```
①移植元の解析 → 要求定義 → アーキテクチャ設計 → プログラム設計 → 実装 → 各テスト → デプロイ
```

この解析結果が、トレーサビリティマトリクスの起点になる。

| M | 内容 | 規模 | 到達点 |
|---|---|---|---|

| M2 | 欠陥ログ | 約1,000行 | PSP の3大生データが揃う |
| M3 | 計算エンジン（A群 ＋ util ＋ Templates変換） | 約8,700行 | 派生指標が自動計算される |
| M4 | PROBE | 約1,200行 | 蓄積データで見積もれる |
| M5 | EV | 約3,000行 | 計画対実績・完了予測 |
| M6 | 仕上げ（サマリ画面・E2E・マニュアル・デプロイ） | 約2,000行 | 第1期完了 |

計算エンジンを後回しにできるのは、**生データの記録がエンジンから独立している**ためである。
時間・欠陥・規模の記録はそれ自体で完結し、エンジンはそれらを入力として
派生指標（歩留まり、欠陥密度、CPI/SPI）を計算する層にすぎない。

PROBE は過去の「見積り規模 vs 実績規模」に回帰分析をかける手法であり、
履歴データがなければ検証できない。M4 到達時点で十数ユニット分の実データが
蓄積されるよう、記録機能を先行させている。

### 議論したい論点（3件）

**論点1：移植仕様書に「実績記録」セクションを入れるか**

Processloop は PSP のツールなので、**この移植プロジェクト自体を PSP で計測する**と筋が通る。見積り行数 vs 実績、所要時間、欠陥を記録すれば、完成後に自分自身の実データとして投入できる。ただし記録の手間は増える。

**論点2：結合テスト仕様書を分割するか**

境界が2種類ある。

- A群内の結合（プリプロセッサ→パーサ→評価器→DataRepository）
- A群とB群の結合（計算エンジンと hier / log / ev）

性質が違うため、2本に分ける案もある。

**論点3：Playwright MCP を使うか**

⑤で「検討中」とされていた点。現時点の私見は次のとおり。

| | 通常の Playwright | Playwright MCP |
|---|---|---|
| 用途 | E2Eテストの実行 | 対話的なブラウザ操作 |
| 総合テストへの適合 | ✅ テストコードとして残る | 探索的な確認向き |
| CI での再現性 | ✅ | 対話が前提 |

**総合テスト仕様書に沿った再現可能なテスト**が目的なら、通常の Playwright が適する。MCP は開発中の動作確認に補助的に使う位置づけが現実的と考える。
