## Q&A 知識カード

### Q. PROBE は履歴データがないと何ができないのか？
A. 何も出力できない。PROBE（PROxy Based Estimating、代理指標にもとづく見積り）は、過去の「見積り規模と実績規模」の組に線形回帰をかけて次の見積りを導く手法であり、t分布を用いて予測区間も算出する。したがって回帰の入力となる履歴が存在しなければ、実装しても機能しない。Processloop では、この性質が実装順序を決める根拠になった。計算エンジンを先に作ると PROBE 実装時に履歴がゼロになるため、データ収集を先行させる順序に変更した。
（出典: 本日の作業から）

### Q. Process Dashboard の生データ記録は、計算エンジンに依存するか？
A. 依存しない。作業時間・欠陥・成果物規模の記録はそれ自体で完結しており、計算エンジンはそれらを入力として派生指標（歩留まり、欠陥密度、CPI、SPI）を計算する層にすぎない。timelog.xml や欠陥ログは、エンジンを通さずに書き出される。この構造的事実により、記録機能を計算エンジンより先に実装しても設計に矛盾が生じないことが確認できた。
（出典: 本日の作業から）

### Q. 個別ユニットの見積りを積み上げたとき、全体の見積りと一致しない場合はどちらが正しいか？
A. 個別の積み上げが正しい可能性が高い。Processloop では第1期の実装規模を7,200行から9,800行と記載していたが、18ユニットの見積りを合計すると19,000行から21,000行になり、約2.2倍の乖離が判明した。個別ユニットの見積りは移植元の実行数に圧縮率を掛けて算出した根拠のある数値であり、合計値の記載のほうが誤りだった。見積りを扱うときは、積み上げと総計を機械的に突き合わせる習慣が必要である。
（出典: 本日の作業から）

### Q. USDM とは何か？
A. Universal Specification Describing Manner の略で、清水吉男氏が提唱した要求仕様の記述法である。要求・理由・説明・仕様グループ・仕様という5つの要素を階層構造で1つの文書にまとめ、要求には必ず理由を添えることを求める。要求は名詞形ではなく動詞形の振る舞いとして書き、要求に含まれる動詞と目的語のペアごとに仕様グループを立てる。Excel の表形式を前提とするが、構造は見出しの階層で表現できるため Markdown にも写せる。
（出典: 本日の作業から）

### Q. USDM で要求に含まれる動詞が8個以上になったらどうするか？
A. 要求を分割する。分割の型は4つあり、時系列分割（時間軸で区切る）、構成分割（機能別や構成別で区切る）、状態分割（状態の概念で区切る）、共通分割（共通する処理を独立させる）である。分割した場合、上位要求と下位要求をそれぞれ別の要求として扱い、下位要求にも理由を書く。動詞の数が仕様グループの数に対応するため、動詞が多すぎると1つの要求が扱う範囲が広くなりすぎる。
（出典: 本日の作業から）

### Q. USDM が避けよと定める表現は何か？
A. 3つある。第1に「等」「etc」であり、現時点で確定できることは全て書き、未確定なら合意する時期を明記する。第2に否定表現であり、「〜しない」という書き方の裏には書かれていない条件分岐が隠れているため、「もし〜の場合は」と書いたら else が何かを必ず考える。第3にペースト作文であり、一部だけ違う仕様をコピーして書くと差異が読み取れなくなるため、条件が複数あるなら表やディシジョンテーブルで整理する。
（出典: 本日の作業から）

### Q. IPA「機能要件の合意形成ガイド」が対象とする工程は要件定義か？
A. 要件定義ではなく外部設計工程である。ガイド自身が、要件定義は発注する側で行われその結果は要件定義書にまとめられると述べたうえで、本ガイドの対象工程を外部設計工程と定めている。合意成熟度の最上位である「完成レベル」も、外部設計工程の成果物の最終承認直前までのレベルと定義されている。したがって「要件定義の書き方」ではなく、要件定義を受けた外部設計で発注者と開発者が認識を揃えるための技法である。
（出典: 本日の作業から）

### Q. 機能要件の合意形成ガイドが扱う技術領域はいくつあるか？
A. 6つである。システム振舞い、画面、データモデル、外部インタフェース、バッチ、帳票であり、このうち後半3つは前身の発注者ビューガイドラインになかった新規追加分である。「概要編」は技術領域ではなく、各分冊を読むための考え方と前提を説明する分冊である。したがって分冊は7点だが技術領域は6つという関係になる。
（出典: 本日の作業から）

### Q. 機能要件の合意形成ガイドが定める「4つの作業」とは何か？
A. 言い切る／聞き切る（コツ44個）、図表に書く（101個）、もれ／矛盾をチェックする（22個）、一緒にレビューする（94個）の4つである。これに加えて「発注者が事前に意識する」（17個）が当初計画の4作業に含まれない追加分として存在し、合計278個になる。合意成熟度のレベルによって4作業の比重が変わり、仕掛レベルでは「言い切る／聞き切る」の比重が高く、充実レベルでは「図表に書く」が高くなる。
（出典: 本日の作業から）

### Q. 機能要件の合意形成ガイドの合意成熟度3レベルは、それぞれ何を意味するか？
A. 仕掛レベルは、発注者が「言い切った」開発者が「聞き切った」と言える状態で、システム化の目的と範囲が明確になっているレベルである。充実レベルは、図表に書いてレビューを繰り返し合意内容が充実していくレベルである。完成レベルは、合意内容が管理され双方が「確認できた」と言える状態で、外部設計工程の成果物の最終承認直前にあたる。
（出典: 本日の作業から）

### Q. 要件定義の概要と個別要求は、どちらを先に書くべきか？
A. 概要が先である。根拠は機能要件の合意形成ガイドにある。同ガイドは仕掛レベルをシステム化の目的と範囲を明確にして認識を共有するレベルと定義し、さらに各レベルでレビュー対象となる工程成果物の対応表で、仕掛レベルでは「一覧」と「共通ルール」が FULL、詳細は PARTIAL とされている。つまり一覧と共通ルールが先で個別の詳細は後という順序が示されている。ただし書ききる必要はなく、仕掛レベルの粒度で薄く書き、詳細は個別要求の作成と並行して育てる。
（出典: 本日の作業から）

### Q. 機能要件の合意形成ガイドの使用条件はどうなっているか？
A. 著作権は IPA が保有し、著作権表示を明記すれば情報システム開発に携わる者が本目的のために無償で複製・再配布できるが、改変・翻案は禁じられている。したがってコツの本文を転記することも、言い換えて掲載することも避けるべきである。Processloop では、著作物にあたらない事実（技術領域の区分、成熟度のレベル名、作業の区分、工程成果物の名称）のみを参照し、レビュー観点は独自に構成した。
（出典: 本日の作業から）

### Q. 機能要件の合意形成ガイドが想定するプロジェクト規模はどのくらいか？
A. 300ファンクションポイント以上、5000万円以上、10名以上、50人月以上を目安としている。Processloop は個人プロジェクトでありこの想定から大きく外れる。ただしガイド自身が、開発規模が小さくメンバも少ないプロジェクトでも発注者と開発者の合意は必要であり、書き方とレビューのコツを参考にしてほしいと述べている。

### Q. Mermaid の Requirement Diagram は何にもとづいているか？
A. SysML バージョン1.6の仕様にもとづいている。要求の種別として requirement、functionalRequirement、interfaceRequirement、performanceRequirement、physicalRequirement、designConstraint を持ち、risk は Low、Medium、High、verifymethod は Analysis、Inspection、Test、Demonstration から選ぶ。関係型は contains、copies、derives、satisfies、verifies、refines、traces である。element 要素は docref を持ち、他の文書の一部と要求を結び付けられる。
（出典: 本日の作業から）

### Q. Mermaid の Requirement Diagram で識別子にハイフンを含めるとどうなるか？
A. 引用符で囲まないと構文エラーになる。`id: FR-HIER-001` のように書くと `Expecting 'NEWLINE', got 'LINE'` というパースエラーが発生する。`id: "FR-HIER-001"` と引用符で囲めば通る。text、type、docref も同様に囲むのが安全である。Mermaid 11.16 で確認した。Processloop の要求 ID はハイフンを含む体系のため、この制約が全ての要求図に影響する。
（出典: 本日の作業から）

### Q. Markdown で Mermaid のコードを4連バッククォートで囲むとどうなるか？
A. GitHub は中身を実行せず、文字列として表示する。4連バッククォートは「これはコード例です」という指示になるためであり、意図した動作ではあるが結果として図が描画されない。Mermaid の書き方を説明する目的で囲むと、説明したい図そのものが見えなくなる。対処は、描画される図を3連バッククォートで直接記述し、ソースの表示を details 要素に畳んで別に置く2段構成にすることである。
（出典: 本日の作業から）

### Q. Mermaid の構文をブラウザなしで検証するにはどうすればよいか？
A. mermaid パッケージの parse 関数を Node.js から呼ぶ。ただし Mermaid は DOM を要求するため、jsdom で最小限の DOM を用意してから import する必要がある。DOM がないと `DOMPurify.addHook is not a function` というエラーが出て、構文とは無関係な失敗として報告される。mermaid-cli（mmdc）は Chrome を必要とするため、レンダリングまで行わず構文だけ確認する場合はパーサを直接呼ぶほうが軽い。
（出典: 本日の作業から）

### Q. draw.io に Mermaid を取り込んだ後、Mermaid ソースを再生成すると編集内容はどうなるか？
A. スタイルとラベルの編集は保持されるが、サイズ・位置・線の経路の変更は上書きされる。2026年7月3日公開の機能で、Mermaid を編集可能な draw.io 図形として取り込めるようになった。図形の見た目を整える作業のうち、色や文字は残るが配置は失われるため、位置調整に労力をかけると再生成のたびに無駄になる。
（出典: 本日の作業から）

### Q. Processloop で作図記法に draw.io を採用しなかった理由は何か？
A. 発注者が存在しないためである。draw.io の最大の利点は、非技術者と画面を見ながらマウス操作で図を修正できることであり、発注者と開発者が一緒にレビューする場面で強く効く。しかし Processloop は個人プロジェクトであり、合意の相手は「半年後の自分」で、その相手は Mermaid を読める。この前提の違いにより利点が働かず、一方で Git の差分が読めることの価値が相対的に高くなる。
（出典: 本日の作業から）

### Q. Processloop で作図記法に PlantUML を採用しなかった理由は何か？
A. Java 実行環境が必要になり依存が増えるためである。Processloop は Node.js と pnpm で環境を統一しており、余計な依存を避けたい。第1期で必要な図（状態遷移、画面遷移、業務フロー、シーケンス、ER図、要求関連図）は全て Mermaid が対応する。ただし第2期のチーム機能で UML の厳密な表現が必要になった時点で再検討する余地は残している。
（出典: 本日の作業から）

### Q. USDM の仕様数は PSP の計測にどう使えるか？
A. 規模の代理指標として使える。USDM は仕様数と作業時間を記録することで生産性を把握でき、以降の工数見積りに使えるとしている。Processloop ではこの移植プロジェクト自体を PSP で計測する方針を採っているため、仕様数は行数と並ぶ規模の指標になり、PROBE の入力として使える可能性がある。要求仕様の Front Matter に spec_count を持たせているのはこのためである。
（出典: 本日の作業から）

### Q. コミットメッセージの本文が長くなりすぎたとき、何を疑うべきか？
A. コミットした差分や文書に既に書いてあることを繰り返している可能性を疑う。本日、要求仕様2本のコミットで本文が10文を超えたが、内容を確認すると IPA の合意成熟度の説明、用語集の中身、仕様の件数、移植しない属性の一覧が含まれており、いずれもコミットした文書内に記載があった。コミットメッセージが答えるべきは「なぜ今これを書いたのか」であって「何を書いたのか」ではない。判断の基準は「差分を見ても分からないか」の一点にある。
（出典: 本日の作業から）

## 語彙・用語リスト（プロジェクト固有）

| 用語 | 定義 |
|---|---|
| USDM（Universal Specification Describing Manner） | 清水吉男氏が提唱した要求仕様の記述法。要求・理由・説明・仕様グループ・仕様を階層構造で1つの文書にまとめ、要求には必ず理由を添える |
| 仕様グループ | USDM で、要求に含まれる動詞と目的語のペアごとに立てる区分。その配下に具体的な仕様を書く |
| 発注者ビュー | 発注者のものの見方。IPA の発注者ビューガイドラインが提唱した概念で、開発者の視点ではなく発注者が理解し検証できる形で設計書を書くことを求める |
| 合意成熟度 | IPA 機能要件の合意形成ガイドが定める、合意の進み具合を表す3段階。仕掛レベル、充実レベル、完成レベル |
| 仕掛レベル | 合意成熟度の第1段階。発注者が言い切り開発者が聞き切った状態で、システム化の目的と範囲が明確になっているレベル |
| 充実レベル | 合意成熟度の第2段階。図表に書いてレビューを繰り返し、合意内容が充実していくレベル |
| 完成レベル | 合意成熟度の第3段階。合意内容が管理され双方が確認できたと言える状態で、外部設計工程の成果物の最終承認直前 |
| 技術領域 | IPA 機能要件の合意形成ガイドが対象とする6区分。システム振舞い、画面、データモデル、外部インタフェース、バッチ、帳票 |
| 工程成果物 | 外部設計工程で作成され合意に用いられる図表。技術領域ごとに想定する種類が定められている |
| コツ | 機能要件の合意形成ガイドが収録する、設計書の記述とレビューに関する知見。合計278個 |
| domains | Processloop の要求仕様 Front Matter の項目。IPA の6技術領域のうち本要求が触れるものを宣言する。該当なしは none |
| spec_count | 同じく Front Matter の項目。本文に含まれる仕様の数。規模の代理指標として PSP 計測に用いる |
| source（Front Matter の） | 移植元の根拠を記録する項目。上流のコミット SHA、根拠となるファイル、対応する解析ドキュメントの ID を持つ |
| Requirement Diagram | Mermaid の図種の1つ。SysML 1.6 にもとづき、要求とその関係を表す。contains、derives、satisfies、verifies、traces などの関係型を持つ |
| 2段構成（Mermaid の） | 描画される図を3連バッククォートで直接記述し、ソースの表示を details 要素に畳んで別に置く書き方。4連バッククォートだけで囲むと図が描画されないため |
