# 多言語対応（en / ja）設計ガイド

Processloop は **英語と日本語の切り替え**を前提に作る。後付けではなく最初から組み込む。

## 採用方針

| 項目 | 決定 |
|---|---|
| 対応ロケール | `en`（ソース） / `ja` |
| 既定ロケール | `en` |
| フォールバック | 未訳キーは `en` を表示（画面を壊さない） |
| ライブラリ | `next-intl`（App Router 前提。雛形は `i18n/starter/`） |
| URL 方式 | パス接頭辞 `/en/...` `/ja/...` |
| 初期判定 | ブラウザの `Accept-Language` → 以降はユーザー選択を優先 |
| リソース形式 | JSON（`i18n/messages/{locale}.json`） |

## フォルダ構成

```
processloop/
├─ i18n/
│  ├─ messages/
│  │  ├─ en.json        ← ソース。キーはまずここに定義
│  │  └─ ja.json        ← 翻訳。en とキー構造を一致させる
│  └─ starter/          ← frontend 初期化後にコピーする設定雛形(.txt)
├─ frontend/            ← Next.js（未初期化）
├─ backend/             ← API（未初期化）
└─ docs/
   ├─ i18n-guide.md     ← このファイル
   └─ i18n-inventory.md ← 移植元リソースの棚卸し
```

## キー設計のルール

- **意味ベースのキー**にする。`nav.dashboard` ○ / `Dashboard` ×
  （英語の文言をキーにすると、英語を直したとき全言語が壊れる）
- 階層は**画面・機能単位**（`nav.*`, `common.*`, `settings.*`, `error.*`）。
- 1画面でしか使わない文言を `common.*` に入れない。使い回す語だけを `common` に置く。
- **文字列連結をしない**。`"合計" + n + "件"` ではなく、プレースホルダ付きの1キーにする。
  日本語と英語で語順が違うため、連結は必ず破綻する。
- 複数形は `next-intl` の ICU 記法で扱う（英語は単複、日本語は単一形）。

## 日本語対応で特に注意する点

- **日付・数値・通貨は必ずフォーマッタ経由**。`YYYY/MM/DD` と `MM/DD/YYYY` の差、
  桁区切りの扱いを手書きしない。
- **文字幅**：日本語は同じ意味でも英語より短く/長くなる。ボタンやラベルを固定幅にしない。
- **改行位置**：日本語は単語境界が無いため、英語前提の折り返し設定だと不自然に切れる。
- **フォント**：日本語グリフを含むフォントを指定する（英字専用フォントだと豆腐になる）。
- **`<html lang>` を必ずロケールに合わせる**（アクセシビリティ・SEO）。
- **ソート順**：日本語の並べ替えは辞書順にならない。`Intl.Collator` を使う。

## 運用ルール

1. 新しい文言は**必ず `en.json` に追加**してから使う。ベタ書き禁止。
2. `ja.json` は `en.json` とキー構造を一致させる。未訳は放置せず、TODO として追う。
3. キーの過不足は CI で検出できるようにする（差分チェックのスクリプトを後で追加）。
4. VSCode の **i18n Ally** 拡張を入れると、未訳キーやハードコード文字列が可視化される。

## ★ ライセンス上の注意

- ここで扱う i18n は**第1層（GPLv3 の UI 文字列）**を対象とする。
- **PSP/TSP のスクリプト・フォーム文言（第2層）は翻訳・改変に CMU/SEI の書面許可が必要**。
  安易に `ja.json` へ取り込まないこと。詳細は棚卸し表とスキルの公開前ゲートを参照。
