## 2. 決定的な理由：PROBE は履歴データがないと成立しない

PROBE（PROxy Based Estimating）は、**過去の実績データに回帰分析をかけて見積もる手法**である。

```
過去の「見積り規模 vs 実績規模」の組 → 線形回帰 → 次の見積り
```

つまり **PROBE を実装しても、履歴データがなければ何も出力できない**。

現行案では、PROBE（B-6）を実装する頃には第1期の大半が終わっている。そこから記録を始めても、**自分のプロジェクトで PROBE を検証する機会がない**。

対してデータ収集を先行させれば、B-6 に到達した時点で**十数ユニット分の実データ**が溜まっている。回帰分析が実際に意味を持つ。

同じことが EV（B-7/B-8）にも言える。計画対実績の比較は、計画と実績の両方が記録されていて初めて成立する。

### 副次的な理由

**1. データモデルの早期検証**

`HierarchyNode` / `TimeLogEntry` / `Defect` の設計が実用に耐えるかは、使ってみないと分からない。終盤で判明すると手戻りが大きい。

**2. 動機の持続**

19,000〜21,000行は長い道のりである。途中で自分のデータが見えるものがあると続けやすい。

**3. ツール自体の説得力**

「PSP のツールを作ったが、開発中は PSP を使っていない」という状態は避けたい。

## 3. 改訂ロードマップ

### M1: データ収集の最小構成（約2,650行）★ドッグフーディング開始点

**到達点**：階層を作り、タスクの作業時間を記録できる。

| ユニット | 内容 | 行数 |
|---|---|---|
| B-9（部分） | Prisma スキーマ（HierarchyNode, TimeLogEntry） | 約250 |
| B-2（部分） | 階層の生成・編集・パス解決 | 約400 |
| B-3（部分） | `PSP-template.xml` からフェーズ一覧を読む | 約200 |
| B-4 | 時間ログ（計測・中断・記録） | 約900 |
| C（部分） | 階層画面・タイマー画面 | 約800 |
| — | 簡易集計（合計時間など） | 約100 |

**この時点で計算エンジンは不要である。** 表示するのは合計時間などの単純な集計のみで、TypeScript で直接書ける（約100行）。

PSP の派生指標（歩留まり、欠陥密度、CPI/SPI）はエンジンが担うが、**生データの記録は独立している**。ここが順序を入れ替えられる根拠になる。

### M2: 欠陥ログ（約1,000行）

**到達点**：欠陥を記録し、フェーズ別の件数が見える。

| ユニット | 内容 | 行数 |
|---|---|---|
| B-5 | 欠陥ログ（混入・除去フェーズ） | 約600 |
| C（部分） | 欠陥ログ画面 | 約400 |

M1 と M2 で、**PSP の3大生データ（時間・欠陥・規模）がすべて記録できる**。

### M3: 計算エンジン（約8,700行）

**到達点**：PSP の派生指標が自動計算される。

```
A-1 プリプロセッサ ✅ → A-3 値の型 → A-4 パーサ → A-5 評価器
  → A-2 動的マクロ → A-7 DataRepository → A-6 組み込み関数
  → B-1 util → B-3（残り） → B-10 Templates変換
```

M1・M2 で溜めた実データに、**PSP の計算式1.2万行が適用される**。ここで初めて歩留まりや欠陥密度が見える。

### M4: PROBE（約1,200行）

**到達点**：溜まった履歴データで見積もれる。

M1 から M3 までの期間で記録した**十数ユニット分のデータ**が、回帰分析の入力になる。

### M5: EV（約3,000行）

**到達点**：計画対実績、完了予測。

### M6: 仕上げ（約2,000行）

サマリ画面、E2E テスト、ユーザーマニュアル、デプロイ。

## 4. 記録方式

**M1 完成までの期間、手動での逐次記録は行わない。**
決定の経緯は [adr/adr-0002-measurement-recording.md](adr/adr-0002-measurement-recording.md) を参照。

| 時期 | 記録方法 |
|---|---|
| A-1（完了済み） | devlog から遡及抽出して登録済み |
| M1 完成まで | **記録しない。** devlog の作成を継続する |
| M1 完成後 | devlog から遡及抽出して一括投入 → 以降は Processloop の UI で記録 |

### なぜ手動記録をしないか

作業のたびに開始・終了・中断時刻を控え、正味時間を計算して CSV に追記する運用は、
**毎日続けることが現実的に困難**である。記録が途切れればデータの一貫性も失われる。

一方、devlog は 2026-07-18 から毎日作成しており運用が定着している。
「つまずき→解決の記録」「調査・実測の記録」を含むため、
**欠陥と規模のデータは後から抽出できる**。

新たに続かない記録を始めるより、既に続いている記録を活かす方が確実である。

### ⚠️ 受け入れる限界

**devlog は作業時間を記録していない。** したがって M1 完成までの期間、
時間データは欠損する。

| 用途 | 影響 |
|---|---|
| **PROBE の回帰** | **なし**（主入力である規模データは回収できる） |
| 欠陥分析 | **なし**（欠陥は回収できる） |
| フェーズ別の時間配分 | M1 まで分析不可 |

PROBE の検証という本ロードマップの目的は、時間データの欠損によって妨げられない。

### データの様式

CSV の列は Prisma スキーマに対応させており、そのまま一括投入できる。
詳細は [psp-data/README.md](psp-data/README.md) を参照。

```
docs/psp-data/
├─ size-log.csv      成果物規模（PROBE の入力）
├─ defect-log.csv    欠陥（混入・発見・分類）
└─ time-log.csv      作業時間（M1 完成後に記録開始）
```

## 6. 開発工程と PSP フェーズの対応

⑤で定義された工程が、**PSP のフェーズにほぼそのまま対応する**。これは偶然ではなく、どちらもソフトウェア開発の工程を表しているためである。

| Processloop の工程 | PSP フェーズ | type |
|---|---|---|
| 移植元の解析 | Planning | plan |
| プログラム設計 | Design | dld |
| （設計レビュー） | Design Review | dldr（appraisal） |
| 実装 | Code | code |
| （コードレビュー） | Code Review | cr（appraisal） |
| 型チェック（`pnpm typecheck`） | Compile | comp（failure） |
| 単体テスト | Test | ut（failure） |
| 事後分析 | Postmortem | pm |

**`pnpm typecheck` が PSP の Compile に対応する**のが面白い点である。型エラーは「コンパイル時に見つかった欠陥」として記録できる。

### 階層の構成案

```
Processloop 第1期
├─ A-1 プリプロセッサ
│  ├─ 解析 / 設計 / 実装 / 型チェック / 単体テスト / 事後分析
├─ A-2 動的マクロ生成
│  └─ （同上）
├─ B-2 hier
└─ …（18ユニット）
```

**ユニット＝タスク、工程＝フェーズ**という対応で、PSP の構造にきれいに収まる。

## 7. リスクと対処

### リスク1：UI が計算エンジン導入時に手戻りする

M1 で作る画面は、エンジン導入後に表示内容が変わる可能性がある。

**対処**：M1 の集計を**エンジンで置き換えやすい形**に隔離する。

```typescript
// M1: 直接計算
export function totalTime(entries: TimeLogEntry[]): number { … }

// M3 以降: エンジン経由に差し替え
export function totalTime(path: string): number {
  return repository.getValue(`${path}/Time`);
}
```

呼び出し側（UI）のインタフェースを変えなければ、差し替えは局所的で済む。

### リスク2：文脈の切り替えコスト

A-1 でエンジンの調査・実装に集中していたため、UI 側に移ると頭を切り替える必要がある。

**対処**：調査済みの資産は消えない。`grammar.txt` の分析も Signals の判断も、M3 でそのまま使える。**保留になるだけで無駄にはならない**。

### リスク3：記録の手間が続かない

手動記録は面倒である。

**対処**：M1 を早く終わらせることが最大の対策になる。それまでは**粒度を粗くする**（1日1行でもよい）。完璧な記録より、続く記録の方が価値がある。
