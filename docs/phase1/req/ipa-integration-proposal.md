## 1. 出典の確認と、事実の訂正

### 参照した資料

| 資料 | 公開 | 作成 |
|---|---|---|
| 発注者ビューガイドライン ver.1.0 | 2007〜2008年 | 国内SI事業者9社「実践的アプローチに基づく要求仕様の発注者ビュー検討会」 |
| 機能要件の合意形成ガイド ver.1.0 | 2010年3月 | IPA/SEC「機能要件の合意形成技法ワーキンググループ」 |

前者が IPA に譲渡され、発注者側企業も加えたWGでの検討を経て後者になった、という系譜である。

### ★ 訂正1：技術領域は6つである

機能要件の合意形成ガイドが扱う技術領域は次の6つで、「概要編」は技術領域ではなく
各分冊を読むための考え方と前提を説明する分冊である。

| # | 技術領域 | 発注者ビューガイドラインにあったか |
|---|---|---|
| 1 | システム振舞い | あり |
| 2 | 画面 | あり |
| 3 | データモデル | あり |
| 4 | 外部インタフェース | **新規追加** |
| 5 | バッチ | **新規追加** |
| 6 | 帳票 | **新規追加** |

### ★ 訂正2：対象工程は「外部設計」であって「要件定義」ではない

ガイドは、要件定義は発注する側で行われ要件定義書にまとめられるとしたうえで、
**本ガイドの対象工程を外部設計工程と定めている**。

合意成熟度の最上位である「完成レベル」も、外部設計工程の成果物の最終承認直前までを指す。

したがって本ガイドは「要件定義の書き方」ではなく、
**要件定義を受けた外部設計で、発注者と開発者が認識を揃えるための技法**である。

### 中身は「コツ」の集合である

ガイドの実体は、設計書の記述とレビューに関する「コツ」を集めたものである。
公開時の報道では 278 個、別の報道では 287 個とされており、数字に揺れがある。
仕様書のテンプレートではない点に注意が必要である。

### 合意成熟度の3レベル

| レベル | 状態 |
|---|---|
| 仕掛レベル | 発注者が「言い切った」、開発者が「聞き切った」と言える。システム化の目的と範囲が明確 |
| 充実レベル | 図表に書いてレビューを繰り返し、合意内容が充実していく |
| 完成レベル | 合意内容が管理され、双方が「確認できた」と言える。外部設計成果物の最終承認直前 |

### 4つの作業（一次資料で確認済み）

コツは合意成熟度の3レベルに加えて、次の4つの作業に分類されている。

| 作業 | コツ数 | 共通フレーム2007 での対応 |
|---|---|---|
| 言い切る／聞き切る | 44 | 要件定義から文書化の要素を具体化・抽出 |
| **図表に書く** | **101** | 文書化 |
| もれ／矛盾をチェックする | 22 | 検証 |
| **一緒にレビューする** | **94** | 共同レビュー |
| （発注者が事前に意識する） | 17 | 当初計画の4作業に含まれない追加分 |
| **合計** | **278** | |

合意成熟度のレベルによって4作業の比重が変わる。
仕掛レベルでは「言い切る／聞き切る」の比重が高く、充実レベルでは「図表に書く」が高くなる。

### 各技術領域が想定する「工程成果物」

ガイドは、外部設計工程で作成され合意に用いられる成果物を「工程成果物」と呼び、
技術領域ごとに想定する種類を定めている。

| 技術領域 | 工程成果物 |
|---|---|
| システム振舞い | システム化業務一覧／システム化業務フロー／システム化業務説明／システム振舞い共通ルール |
| 画面 | 画面一覧／画面遷移／画面レイアウト／画面入出力項目一覧／画面アクション明細／画面遷移・レイアウト共通ルール |
| データモデル | ER図／エンティティ一覧／エンティティ定義／CRUD図 |
| 外部インタフェース | 外部システム関連図／外部インタフェース一覧／外部インタフェース項目説明／外部インタフェース処理説明 |
| バッチ | バッチ処理一覧／バッチ処理フロー／バッチ処理定義／バッチ処理共通ルール |
| 帳票 | 帳票一覧／帳票概要／帳票レイアウト／帳票項目説明／帳票編集定義 |

### ⚠️ ガイドの使用条件

ガイドの著作権は IPA が保有する。著作権表示を明記すれば、
情報システム開発に携わる者が本目的のために無償で複製・再配布できるが、
**改変・翻案は禁じられている**。

したがって Processloop では、**コツの本文を転記も言い換えもしない**。
参照するのは著作物にあたらない事実（技術領域の区分、成熟度のレベル名、
作業の区分、工程成果物の名称）に限る。

レビュー観点は [review-checklist.md](review-checklist.md) として独自に構成した。

### ⚠️ 想定規模との差

ガイドは 300FP 以上、5000万円以上、10名以上、50人月以上のプロジェクトを目安としている。
Processloop は個人プロジェクトであり、この想定から大きく外れる。

ただしガイド自身が、開発規模が小さくメンバも少ないプロジェクトでも
発注者と開発者の合意は必要であり、書き方とレビューのコツを参考にしてほしいと述べている。

## 2. USDM と IPA ガイドの関係

両者は競合せず、**直交して補完し合う**。

| | USDM | IPA ガイド |
|---|---|---|
| 定めるもの | 要求と仕様の**記述構造** | 設計書の**記述とレビューのコツ** |
| 軸 | **縦**（要求 → 仕様のトレーサビリティ） | **横**（6技術領域の網羅性） |
| 単位 | 1要求 | 1図表・1観点 |
| 対象工程 | 要求仕様（設計の前） | 外部設計 |

### 工程が重なる理由

USDM は、設計の手戻りを防ぐために**設計に入る前に仕様を出し切る**ことを求める。
USDM における「仕様」とは、設計の概要にあたる粒度で What を定義したものである。

つまり **USDM の仕様欄に書かれる内容は、IPA ガイドが外部設計で合意せよという内容とほぼ同じ範囲**にある。

```
        要件定義          外部設計          実装
IPA:                  ├─ 合意形成のコツ ─┤
USDM:  ├─ 要求 ─┤├──── 仕様 ────┤
                        （重なる範囲）
```

この重なりがあるため、**IPA の6技術領域を USDM の仕様の網羅チェックに転用できる**。

## 3. 統合の設計

### 統合点1：6技術領域を「網羅性の軸」にする

USDM の仕様グループは**要求に含まれる動詞**から立てる。これは縦の構造である。
それとは別に、**その要求が6技術領域のどれに触れるか**を宣言し、記述漏れを検出する。

Front Matter に `domains` を追加する。

```yaml
domains:
  - behavior      # システム振舞い
  - screen        # 画面
  - data_model    # データモデル
  # - external_if # 外部インタフェース
  # - batch       # バッチ
  # - report      # 帳票
```

これにより、次の検証が機械的にできる。

- `screen` を宣言した要求に画面遷移図があるか
- `data_model` を宣言した要求にエンティティの定義があるか
- 全要求を通して、扱われていない技術領域はないか

### 統合点2：`status` を合意成熟度に対応させる

既存の `status` の値はそのままに、IPA の合意成熟度で**意味を定義し直す**。

| `status` | 対応する合意成熟度 | Processloop での判定基準 |
|---|---|---|
| `draft` | 仕掛レベル | 要求の範囲と目的が書けた。仕様は未着手または途中 |
| `reviewed` | 充実レベル | 仕様と図表が揃い、レビューを一巡した |
| `approved` | 完成レベル | 仕様の抜けと曖昧さが解消し、実装に引き渡せる |
| `obsolete` | （対応なし） | 廃止された要求 |

値を増やさず意味づけだけ与えるため、既に作成した JSON Schema の変更は不要である。

### 統合点3：図表を Mermaid で持つ

IPA ガイドは技術領域ごとに具体的な図表を挙げている。Processloop で該当するものを整理する。

| 技術領域 | IPA が挙げる図表 | Processloop での記法 |
|---|---|---|
| システム振舞い | 業務フロー、システムフロー、機能一覧 | Mermaid（flowchart, stateDiagram, sequenceDiagram） |
| 画面 | 画面一覧、画面レイアウト、画面遷移図、入出力項目一覧 | 画面遷移図は Mermaid。**レイアウトは別途** |
| データモデル | ER図、エンティティ一覧、CRUD図 | ER図は Mermaid（erDiagram）。CRUD図は表 |

⚠️ **画面レイアウトは Mermaid で書けない。** 実装後のスクリーンショット、
または `frontend` の実装そのものを参照とする。第1期では画面が5つしかないため、
実装を正とし、要求仕様には項目一覧のみを書く方針を提案する。

### 統合点4：「コツ」をレビュー観点に変換する

278個すべてを取り込むのは現実的でない。また原文の転記は著作権上避けるべきである。

**Processloop に効く観点だけを、自分の言葉で抽出したチェックリスト**を作る。
レビュー時（`draft` → `reviewed` の移行時）に使う。

USDM 自身が挙げる注意点（「等」「否定表現」「ペースト作文」）と統合し、
1つのレビューチェックリストにまとめる。

### 統合点5：「概要編」に相当する文書を置く

IPA ガイドが概要編を置いているのと同様に、個別要求の上位に**全体を示す文書**を置く。

1要求1ファイルの方式では、要求が20〜30本に分散する。
**システム化の目的と範囲、用語、技術領域のカバレッジ**を1箇所にまとめないと、
全体像が失われる。

## 5. Processloop への適用 — 6技術領域のうち何が該当するか

**全部を埋めようとすると形骸化する。** 正直に整理する。

| 技術領域 | 第1期での該当 | 内容 |
|---|---|---|
| **システム振舞い** | ✅ **該当** | 計測の状態遷移、階層操作、計算式の評価フロー |
| **画面** | ✅ **該当** | 5画面（階層・タイマー・欠陥ログ・PROBE・サマリ） |
| **データモデル** | ✅ **該当** | 4モデル（HierarchyNode / TimeLogEntry / Defect / DataValue） |
| 外部インタフェース | △ **一部** | Route Handlers（内部API）のみ。外部システム連携は第2期 |
| バッチ | ❌ **該当なし** | 第1期にバッチ処理はない |
| 帳票 | ❌ **該当なし** | EVレポートは画面。印刷とエクスポートは第1.5期以降 |

**第1期で本格的に扱うのは3領域**である。外部インタフェースは Route Handlers に限定し、
OpenAPI で別管理する（[README.md](README.md) の第8節）。

バッチと帳票は、該当が生じた時点（第1.5期以降）で `domains` に追加する。

## 6. ⚠️ Processloop 固有の事情 — 「発注者」が存在しない

IPA ガイドは**発注者と開発者が別人であること**を前提に設計されている。
「発注者ビュー」とは発注者のものの見方であり、目的は両者のシステム像の共有である。

Processloop は個人プロジェクトであり、**発注者と開発者が同一人物**である。
この前提のずれをどう扱うか。

### 提案：合意の相手を「将来の自分」と読み替える

| IPA の前提 | Processloop での読み替え |
|---|---|
| 発注者と開発者の認識のずれ | **書いた時点の自分と、実装する時点の自分のずれ** |
| 発注者が理解できる表現 | **半年後の自分が読んで分かる表現** |
| 一緒にレビューする | **日を改めて読み返す**（USDM も要求引き出しと仕様化を分けることを推奨） |

この読み替えには根拠がある。USDM は、要求の引き出しと仕様化を明確に分けることを
推奨している。**日を分ければ、書き手と読み手は実質的に別人になる。**

### 読み替えても失われないもの

- 6技術領域による網羅性のチェック
- 図表による表現
- 曖昧さを排除する観点

### 読み替えで失われるもの

- 発注者へのヒアリング技法（該当者がいない）
- 合意の記録と管理（相手がいない）

⚠️ ただし**移植プロジェクトには実質的な「発注者」がいる**とも言える。
**移植元の挙動**である。「移植元がどう振る舞うか」を正確に聞き取り、
要求として書き起こす作業は、発注者ビューのヒアリングに近い。

この観点では、既存の Front Matter の `source`（移植元のファイルと上流SHA）が
**発注者の発言記録に相当する**。

## 9. 論点への結論（2026-07-20 決定）

### 論点1：`domains` は必須とする

**決定：必須とする。** 該当する技術領域がない場合は `none` を単独で指定する。

```yaml
# CON-LICENSE-001 のような制約要求
domains:
  - none
```

JSON Schema には、`none` を他の領域と併記できない制約を入れた。
必須にすることで「宣言し忘れ」と「該当なしと判断した」を区別できる。

### 論点2：レビュー観点は30項目とする

**決定：合計30項目。** 内訳は次のとおりで、[review-checklist.md](review-checklist.md) に定めた。

| 段階 | 観点 | 項目数 |
|---|---|---|
| `draft` → `reviewed` | 構造とUSDM（観点1〜5） | 15 |
| `reviewed` → `approved` | 技術領域と移植固有（観点6〜9） | 15 |

技術領域ごとの観点はその `domains` を宣言した要求にのみ適用するため、
1つの要求に実際に適用されるのは20前後になる。

⚠️ 前述のとおり IPA ガイドは改変・翻案を禁じているため、
観点はコツの転記ではなく独自に構成した。

### 論点3：`overview.md` を先に書く

**決定：`overview.md` が先。** 根拠は一次資料にある。

ガイドは合意成熟度の仕掛レベルを、**システム化の目的と範囲を明確にして認識を共有するレベル**と定義し、
要件定義が完了していなければこのレベルで補うとしている。

さらに、各レベルでレビュー対象となる工程成果物の対応表では、
**仕掛レベルで「一覧」と「共通ルール」が FULL、詳細は PARTIAL** とされている。

| レベル | 揃っているべきもの |
|---|---|
| 仕掛 | 業務一覧・画面一覧・エンティティ一覧・各共通ルール（FULL）／フローとレイアウト（PARTIAL） |
| 充実 | すべての工程成果物が記述欄まで埋まっている |
| 完成 | 異なる役割から見た操作と運用まで整合している |

つまり **「一覧」と「共通ルール」が先で、個別の詳細は後**という順序が示されている。

`overview.md` に書くのは一覧と共通ルールにあたる内容であり、個別要求は詳細にあたる。
したがって `overview.md` が先になる。

**理解の早さという観点でも同じ結論になる。** 要求の一覧がないまま個別要求を書くと、
粒度がばらつき、全体像を後から再構成することになる。

ただし**書ききる必要はない**。仕掛レベルの粒度、すなわち
