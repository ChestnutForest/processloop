# 要求仕様のレビュー観点

要求仕様を `draft`（仕掛レベル）から `reviewed`（充実レベル）へ進めるとき、
および `reviewed` から `approved`（完成レベル）へ進めるときに使うチェックリストである。

---

## この文書の位置づけと出典の扱い

⚠️ **本チェックリストは Processloop 独自に作成したものである。**

IPA「機能要件の合意形成ガイド」は278個のコツを収録しているが、
同ガイドの使用条件は改変・翻案を禁じている。したがって本書は**コツの転記でも言い換えでもない**。

参照しているのは、著作物ではない事実にあたる次の要素のみである。

- 6技術領域という区分と、その名称
- 合意成熟度の3レベル（仕掛・充実・完成）という区分と、その名称
- 4つの作業（言い切る／聞き切る、図表に書く、もれ／矛盾をチェックする、一緒にレビューする）という区分
- 各技術領域が想定する「工程成果物」の名称

観点そのものは、USDM が明示する注意点と、Processloop 固有の事情から独自に構成した。

**コツを実際に活用したい場合は、一次資料を直接参照すること。**
無償で複製・再配布が認められており、著作権表示を明記すれば利用できる。

## レビューの進め方

USDM は要求の引き出しと仕様化を分けることを推奨している。
Processloop は個人プロジェクトであり発注者と開発者が同一人物であるため、
**書いた日と別の日に読み返す**ことでレビューの体裁を作る。

| 移行 | 使う観点 | 目安 |
|---|---|---|
| `draft` → `reviewed` | 観点1〜5（構造とUSDM） | 書いた翌日以降 |
| `reviewed` → `approved` | 観点6〜9（技術領域と整合） | 実装着手の直前 |

---

## 観点1：要求は振る舞いとして書けているか（4項目）

- [ ] **R-01** 要求文の動詞がすべて動詞形になっているか（「表示」ではなく「表示する」）
- [ ] **R-02** 目的語と動詞が交互に連なり、処理の流れが読み取れるか
- [ ] **R-03** 動詞の数を数えたか。8個以上なら要求を分割したか
- [ ] **R-04** イベントに始まり、処理が止まるところまでが1つの要求に収まっているか

## 観点2：理由が要求に固有か（2項目）

- [ ] **R-05** 「効率化のため」のような一般論になっていないか
- [ ] **R-06** 移植元がその挙動を持つ根拠、または PSP の方法論上の必然性が示されているか

## 観点3：曖昧な表現がないか（3項目）

USDM が明示的に避けよと述べる3つに対応する。

- [ ] **R-07** 「等」「etc」を使っていないか。使うなら確定時期を明記したか
- [ ] **R-08** 否定表現（「〜しない」）の裏に、書かれていない条件分岐が隠れていないか
- [ ] **R-09** 一部だけ違う仕様をコピーして書いていないか。条件が複数なら表にしたか

## 観点4：仕様が要求から導出されているか（3項目）

- [ ] **R-10** すべての仕様が、要求に含まれる動詞のいずれかに対応しているか
- [ ] **R-11** 要求の範囲を超えた仕様が紛れ込んでいないか
- [ ] **R-12** 仕様グループが、要求の動詞と目的語のペアから立てられているか

## 観点5：仕様の粒度は適切か（3項目）

- [ ] **R-13** 各仕様から、実装の作業と所要時間が見積もれるか
- [ ] **R-14** 各仕様から、テストの手段が導出できるか
- [ ] **R-15** 1つの仕様に複数の内容が詰め込まれていないか

---

以下は `reviewed` → `approved` で使う。

## 観点6：システム振舞い（3項目）

`domains` に `behavior` を含む要求に適用する。

- [ ] **B-01** 状態が複数あるなら、すべての状態と遷移を図に表したか
- [ ] **B-02** 異常時の振る舞いを書いたか（入力が不正、対象が存在しない、処理が中断された）
- [ ] **B-03** 同時に複数の操作が起きた場合の扱いを決めたか

## 観点7：画面（4項目）

`domains` に `screen` を含む要求に適用する。

- [ ] **S-01** 画面に入出力する項目を、桁数と型を含めて一覧にしたか
- [ ] **S-02** 画面遷移の起点となる操作と、遷移先を明示したか
- [ ] **S-03** 操作の結果として何が起こるかを、画面ごとに書いたか
- [ ] **S-04** 多言語対応が必要な文言に、i18n のキーを割り当てたか

## 観点8：データモデル（4項目）

`domains` に `data_model` を含む要求に適用する。

- [ ] **D-01** エンティティと属性を一覧にし、型と桁を定めたか
- [ ] **D-02** エンティティ間の関連と、その多重度を示したか
- [ ] **D-03** データの上限・下限、正常値と異常値の基準を書いたか
- [ ] **D-04** どの機能がどのエンティティを生成・参照・更新・削除するかを整理したか

## 観点9：移植固有の整合（4項目）

すべての要求に適用する。Processloop が移植プロジェクトであることに由来する。

- [ ] **P-01** `source` に移植元のファイルと上流SHA を記載したか
- [ ] **P-02** 移植元と挙動を変える箇所を「説明」に書き、その判断理由を添えたか
- [ ] **P-03** 移植しない部分があるなら、その理由を書いたか
- [ ] **P-04** 移植元に第三者ライセンスのコードが含まれていないか確認したか

## 観点の総数

| 段階 | 観点 | 項目数 |
|---|---|---|
| `draft` → `reviewed` | 1〜5 | 15 |
| `reviewed` → `approved` | 6〜9 | 15 |
| **合計** | | **30** |

技術領域ごとの観点（6〜8）は、その `domains` を宣言した要求にのみ適用する。
したがって1つの要求に適用される項目は、実際には20前後になる。

---

## 使い方

要求仕様ファイルの末尾に、通過した観点を記録する必要はない。
**チェックリストは通過の証跡ではなく、見落としを防ぐ道具**として使う。

ただし `status` を変更するコミットでは、
コミットメッセージにレビューで見つけた欠陥を書き残すことを推奨する。
[ADR-0002](../../adr/adr-0002-measurement-recording.md) により、
devlog から欠陥を遡及抽出する方針を採っているためである。
