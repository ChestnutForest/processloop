# アーキテクチャ仕様書（ARC）目次案

工程ゲート G1 の通過条件に「要求仕様と ARC が承認され、TM の骨格ができている」とあるが、
ARC の内容は [deliverables-proposal.md](../deliverables-proposal.md) に1行の要約があるのみで、
何を書けばよいかが定まっていない。

本書は **ARC の目次**を定める。目次が固まってから本体を書く。

配置先は `docs/phase1/arc-architecture.md` を予定する。

**2026-08-10 に段階分割の方針を決定した**（第5章）。
残る3つの論点は、それぞれの段階の直前に判断する（第6章）。

---

## 1. なぜ目次を先に定めるか

ARC は G1 の通過条件でありながら、実質的に **M1 の設計を終える作業**になる。
Prisma スキーマ全体、計算エンジンの層構成、Signals の採用範囲を決めることになるためである。

書き始めてから範囲を決めると、際限なく広がるか、逆に必要な項目が抜ける。
**目次を先に固定し、各節の分量の目安も決めておく。**

---

## 2. ⚠️ 混同を避けるべき2文書

**`architecture-analysis.md` は ARC ではない。**

| 文書 | 対象 | 性質 |
|---|---|---|
| `architecture-analysis.md` | **移植元** Process Dashboard | 解析報告（現状の記述） |
| `arc-architecture.md`（ARC） | **移植先** Processloop | 設計仕様（これから作るものの定義） |

名前が似ているため取り違えやすい。ARC は移植元の構造を前提としつつ、
**Processloop として何をどう作るか**を定める文書である。

トレーサビリティ上も役割が違う。

```
ANA（解析）→ FR/NFR/CON（要求）→ ARC（アーキテクチャ設計）→ PRT（プログラム設計）→ SRC（実装）
  ↑                                    ↑
architecture-analysis.md          arc-architecture.md
```

## 5. 段階分割（2026-08-10 決定）

**ARC は3段階に分けて書く。全部を書ききってから G1 とはしない。**

### 決定の根拠

**根拠1: G1 の条件が「完成」を求めていない**

工程ゲートの定義は「要求仕様と ARC が**承認され**、TM の**骨格**ができている」である。
3条件のいずれも完成ではなく、揃った状態を求めている。段階分割はこの設計と一致する。

**根拠2: IPA の合意成熟度と一致する**

仕掛レベルは一覧と共通ルールが FULL、詳細は PARTIAL と定められている。
段階1の範囲（一覧・ER図・遷移図）がこれに当たる。
`overview.md` を個別要求より先に書いた根拠と同じ論理であり、方針が一貫する。

**根拠3: 一括作成は ADR-0001 と矛盾する**

一括作成を選ぶと、計算エンジンの設計まで G1 の条件に含まれる。
しかし ADR-0001 でデータ収集を先行させると決めた以上、
**M3 まで使わない設計を M1 の前に確定させるのは筋が通らない**。

### 段階1：G1 のために必要（仕掛レベル相当）★次の作業

| 章 | 必要な深さ |
|---|---|
| 第1章 位置づけ | 全部 |
| 第2章 全体構成 | 全部 |
| 第3章 データモデル | **エンティティ一覧と ER図まで**（属性の詳細は後） |
| 第6章 画面 | **画面一覧と遷移まで** |
| 第8章 テスト方式 | 境界の定義のみ |
| 第10章 決定の一覧 | ADR への参照のみ |

### 段階2：M1 着手前までに必要（充実レベル相当）

| 章 | 追加する内容 |
|---|---|
| 第3章 | 属性の定義、Prisma スキーマ、CRUD図 |
| 第5章 | 永続化の全体 |
| 第7章 | API の一覧 |
| 第9章 | 横断的な方針 |

### 段階3：M3 着手前でよい

| 章 | 内容 |
|---|---|
| 第4章 計算式エンジン | 5層の詳細。M1 では使わないため |

**この分割により、G1 の通過を早められる。**
計算式エンジンの設計を M1 の着手前に確定させる必要はない。

## 6. 残る論点と、判断の時期

段階分割を決めたことで、残る3つの論点は**それぞれの段階の直前に判断すればよくなった**。
判断材料が揃わないうちに決めると、後で作り直しになる。

| 論点 | 判断の時期 | 段階1での暫定対応 |
|---|---|---|
| 第4章を ARC に含めるか | 段階3の直前 | 目次に残すが執筆しない |
| `DataValue` の確定時期 | 段階2の直前 | 一覧に名前を挙げ「M3 で確定」と注記 |
| SCR との境界 | 画面仕様書の着手時 | 画面遷移図を ARC に置く（暫定） |

### 論点2：第4章（計算式エンジン）を ARC に含めるか

M3 まで使わない内容を ARC に置くか、別文書に切り出すか。

`architecture-analysis.md` に既に5層構造の解析があるため、
**ARC では「移植方針」だけを短く書き、詳細は M3 の移植仕様書に譲る**案もある。

**判断の時期**: 段階3の直前（M3 着手前）。段階1では目次に残すのみとする。

### 論点3：`DataValue` モデルをいつ確定させるか

計算式エンジンが扱う値を保持するモデルであり、エンジンの設計に依存する。

- **案A**: M1 では作らない。M3 で追加する
- **案B**: 最小限の形で作っておき、M3 で拡張する
- **案C**: 第1期全体を見越して今確定させる

⚠️ 案Cは、エンジンの設計が固まっていない段階では難しいと考える。

**判断の時期**: 段階2の直前。段階1ではエンティティ一覧に名前を挙げ、
「M3 で確定する」と注記するにとどめる。ER図にも「M1 では未使用」と添える。

### 論点4：画面仕様書（SCR）との境界

ARC の第6章と画面仕様書の役割分担をどこで切るか。

現時点の案は「ARC は構成と方針、画面仕様書は入出力項目と操作の詳細」だが、
画面遷移図をどちらに置くかは決めていない。

**判断の時期**: 画面仕様書の着手時。

**段階1での暫定対応**: 画面遷移図を ARC に置く。遷移は画面間の関係であり、
アーキテクチャの一部と解釈できるためである。
画面仕様書を書く段階で、重複が生じるようなら見直す。
